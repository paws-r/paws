# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Scope of this file

This file covers **`paws.common`** and **`make.paws`** only — the two hand-written packages in this repo. Everything else at the repo root (`cran/`, `paws/`, `docs/`, `vendor/botocore/`) is generated output or vendored data, not source to edit directly:

- `cran/paws.<category>/` and `cran/paws/` — the actual CRAN-distributed AWS SDK packages, generated from `vendor/botocore`'s API models by `make.paws` via `make build`/`make install` (see `Makefile`, `DEVELOPER_GUIDE.md`). Don't hand-edit files under `cran/*/R/`; a regen will overwrite them. Service-specific hand-written behavior lives in `make.paws/R/custom/*.R` (copied wholesale into the generated package) or `paws.common/R/custom_*.R` (non-user-visible, run at request time), not in the generated output.
- `paws/` — also generated by `make.paws` (it's `make_sdk()`'s `out_doc_dir`, cleared and rewritten on every `make build`), but it's a *documentation* output, not an installable mirror of `cran/paws/`: it carries examples and return-value docs that a separate website repo builds the paws-r.github.io site from. Not source to edit directly, same as `cran/`.
- `docs/` — hand-maintained documentation markdowns (configuration, credentials, retries, paginators, etc.) that also feed that website.
- `vendor/botocore` — a git submodule holding the AWS API models `make.paws` generates from, one `service-2.json` (plus `paginators-1.json`, `waiters-2.json`, etc.) per service under `vendor/botocore/botocore/data/<service>/<version>/`. It's read-only input, not edited here — if a service's generated operations/parameters are wrong, the fix is in `make.paws`'s reading/processing of this data (`R/read_api.R`, `R/process_api.R`), not in the JSON itself.

If you're asked to add an AWS-service-level feature (not a `paws.common` request-handling change), check `make.paws/R/custom/*.R` first — that's almost always the right place. To onboard a brand-new service (e.g. a new `bedrock-*` API), add it to the appropriate category's `services` list in `make.paws/inst/extdata/packages.yml` — that file is what drives which `vendor/botocore` services get generated into which `cran/paws.<category>` package.

## Architecture

- **`paws.common`** is the shared runtime every generated `paws.<category>` package depends on — the R equivalent of what `botocore` is to `boto3`/the AWS CLI. It has no knowledge of individual AWS services: it resolves credentials/region/config, builds and signs HTTP requests from the SDK interface, sends them, and unmarshals responses. The request lifecycle is a handler pipeline with named stages (`validate`, `build`, `sign`, `send`, `validate_response`, `unmarshal`, `unmarshal_error`, `retry`, `complete`; see `R/handlers.R`, `R/service.R`). Generated per-service code only attaches handlers to these stages (e.g. "serialize as JSON", "sign with SigV4") — the pipeline, HTTP client, and retry logic are all `paws.common`.
- Request building/signing: `R/client.R` (endpoint/region resolution, dualstack, ARN access points via `R/custom_s3.R`), `R/signer_v4.R`/`signer_v1.R`/`signer_s3*.R` (SigV4 and legacy signing), `R/credentials.R`/`credential_*.R` (credential provider chain).
- Performance-sensitive, frequently-called utilities (string manipulation, URL encoding/parsing, JSON building, endpoint resolution, etc.) are implemented in C++ via Rcpp rather than R — see `paws.common/src/*.cpp`.
- **Parallel transfers** (`R/parallel.R`, `R/transfer.R`; design and measurements in `plans/s3_transfer_manager.md`): `request_only(svc)` returns a copy of a client whose config has `send = FALSE`, so `request_only(svc)$upload_part(...)` returns the signed `Request` instead of sending it (`send_request()` returns early after `sign()` when `request$config$send` is `FALSE`). The setting lives on the client's config, not in global state, so requests the pipeline makes for itself (credential refresh, bucket-region lookup) use a different config and are sent normally. It only works for plain generated operations that return what `send_request()` gives them (`upload_part`, `get_object`); wrap results in `prepared()` to check. `perform_requests()` runs a batch concurrently on a `curl` pool (`perform_batch()`/`run_pool()` in `R/parallel.R`; `curl::multi_run()` returns to R every 0.25s and checks for Ctrl-C itself), re-queueing retryable failures with one shared backoff per round; `complete_request()` feeds a response back through the rest of the pipeline via the one-shot `request$prefetched_response` read by `send_handler`. The serial path stays on httr2 (`as_httr2_request()` in `R/net.R`); `as_curl_handle()` mirrors it for the pool (same `curl::new_handle()` defaults, method, body, headers, timeouts, and no default `Content-Type`), and responses are rebuilt with `httr2::response()` so `as_http_response()` and its case-insensitive headers are shared. Checked byte-for-byte against the serial path with a local HTTP server; keep the two in step when changing either. `multipart_upload_file()`/`multipart_download_file()` are the exported engines behind S3 `upload_file`/`download_file` (the wrappers live in `make.paws/R/custom/s3.R`). Streaming (`stream_api`) operations are refused. R stays single-threaded: only the network transfer overlaps, not reading/checksumming/signing. We deliberately don't use `httr2::req_perform_parallel`: it swallows the first Ctrl-C into its own drain, which could hang until a second one.
- S3 wrong-region redirects: `s3_redirect_from_error` (`send` stage) re-resolves the endpoint, re-signs and re-sends once, and records the bucket's region in the package-level `s3_region_cache` (`R/cache.R`, keyed `<partition>/<bucket>`, cleared by `paws_reset_cache()`); `s3_redirect_from_cache` (first `build` handler) applies a cached region to later requests so they aren't redirected again, mirroring botocore's `S3RegionRedirectorv2`. It skips custom endpoints, access-point ARNs and already-redirected requests, and does not mark requests as redirected so a stale entry heals on the next redirect. This matters for parallel transfers: without it every part is sent to the wrong region first and re-sent one at a time.
- S3 SigV4 signs `UNSIGNED-PAYLOAD` instead of a SHA256 of the body over HTTPS when a checksum header (`x-amz-checksum-*`, not `-algorithm`/`-type`, or `Content-MD5`) is present, mirroring botocore (`s3_skip_payload_signing()` in `R/signer_v4.R`); `s3_payload_signing_enabled` in the service config overrides it. Over plain http the body is still hashed.
- `type()`/`tag_get()` and the `tags` attribute (`R/tags.R`, `R/struct.R`) drive both the build and parse dispatch (structure vs. list vs. map vs. scalar) and most of the service-level metadata (locationName, idempotencyToken, payload, etc.) that make.paws attaches when generating `*_input`/`*_output` constructors.
- **`make.paws`** parses the JSON API models under `vendor/botocore/botocore/data` and generates, per service: the service constructor, operation functions, and input/output interface constructors, writing them into `cran/paws.<category>/R/`. It's also responsible for filling in metadata the API JSON doesn't carry itself (e.g. endpoints) — see `R/read_api.R`/`R/process_api.R` for where that's patched in. `R/custom/*.R` here (e.g. `s3.R`) holds hand-written, user-visible functions (like `generate_presigned_url`/`generate_presigned_post`/`download_file`) that get copied wholesale into the generated package rather than generated from the API model.

## Commands

- `make common` — install `paws.common` from source (`cd paws.common && devtools::document(); devtools::install()`).
- `make test-common` — run `paws.common`'s test suite + `devtools::check('paws.common')`.
- `make codegen` — install `make.paws` from source.
- `make test-codegen` — run `make.paws`'s test suite.
- `make unit` — both of the above test targets.
- Single test file: `devtools::test_file('paws.common/tests/testthat/test_X.R')` (package must already be installed/loadable — `pkgload::load_all('paws.common')` first if you want to test against uninstalled source changes without reinstalling).
- R CMD check equivalent used in CI: `rcmdcheck::rcmdcheck('paws.common', args = c("--no-manual", "--as-cran"), error_on = "warning")` — CI fails on **warnings**, not notes, so notes aren't blocking (see `.github/workflows/unit-tests.yml`).
- Format: `air format .` (Air; config in `air.toml`, 90-char lines — this supersedes the 80-char/styler guidance in `DEVELOPER_GUIDE.md`, which is stale).
- Regenerate docs/NAMESPACE after editing roxygen comments: `roxygen2::roxygenise("paws.common")` or `roxygen2::roxygenise("make.paws")` (`devtools::document()` is also fine — it calls roxygen2 under the hood).
- After editing any `paws.common/src/*.cpp` file: `Rcpp::compileAttributes('paws.common')` to regenerate `R/RcppExports.R`/`src/RcppExports.cpp`, then reinstall/`pkgload::load_all()` before a test will reflect the change.
- `make build`/`make install`/`make integration` exist for regenerating and testing the full SDK (`cran/`, `paws/`) but are out of scope here — don't run them unless explicitly asked; `make build` in particular is slow. `script/post_build_formatting.R` runs after a regen (CI does this on every build) to clean up formatting issues `make.paws` itself misses. `script/codecov.R` generates the CI code coverage reports.

## Working conventions

- Never make live AWS calls (e.g. `make integration`) without explicit approval — those require real credentials and hit real AWS.
- Local S3 testing without AWS is fine: MinIO is installed via Homebrew (`/home/linuxbrew/.linuxbrew/bin/minio`, not on the tool PATH). The user may already have their own instance running on `:9000` with data in `~/minio-data`; **don't use or modify it**. Start a throwaway one on another port with scratch storage (`MINIO_ROOT_USER=... MINIO_ROOT_PASSWORD=... minio server <scratch-dir> --address 127.0.0.1:9100`), point a client at it with `config = list(endpoint = "http://127.0.0.1:9100", s3_force_path_style = TRUE, region = "us-east-1", credentials = ...)`, and stop only the process you started. It is plain http, so HTTPS-only behaviour (e.g. unsigned payloads) needs unit tests or `s3_payload_signing_enabled = FALSE` to emulate.
- `DESCRIPTION` may carry the maintainer's uncommitted hand edits (e.g. `Version:`). Don't `git checkout` it to undo a side effect. After `roxygen2::roxygenise()` revert only what it changed incidentally (`Config/roxygen2/version`); a new `R/*.R` file legitimately adds a `Collate:` entry.
- Add a `NEWS.md` entry (`paws.common/NEWS.md`) for user-facing `paws.common` changes, matching the existing style: one-line bullet, backtick code refs, `(#NNN)` issue link and `Thanks to @user for raising issue` when there's a reporter to credit.
- Never bump `Version:` in a `DESCRIPTION` or touch CRAN submission steps (`devtools::check(cran=TRUE)`, `devtools::submit()`, GitHub releases) — versioning and release are maintainer-only, done manually per `DEVELOPER_GUIDE.md`.
- make.paws changes and regenerated-code changes belong in separate PRs (already called out in `DEVELOPER_GUIDE.md` — regenerating touches many files, so it shouldn't be mixed with the generator fix that caused it).

## Known pitfalls

- **Bare `.s3`-style references in `make.paws/R/custom/*.R` are the default and are fine in the built package.** `.s3` is a package-level object in `paws.storage` (from `s3_service.R`), so `s3_download_file`, `s3_upload_file` etc. use `.s3$get_object_input(...)` / `.s3$operations` directly. They do **not** resolve when the custom file is `source()`'d standalone (e.g. `make.paws`'s own unit tests, or a throwaway script) unless you define `.s3` first, e.g. `env$.s3 <- get(".s3", envir = getNamespace("paws.storage"))` before `sys.source()`. Only functions that have a standalone unit test need to avoid the bare reference: `s3_generate_presigned_url`/`s3_generate_presigned_post` resolve `.s3` dynamically via `get(".s3", envir = getNamespace("paws.storage"))` for that reason. Don't use the dynamic form otherwise; it hard-codes the package name for no benefit.
- **Operations find their client config by inspecting the call, so custom functions can't just call sibling operations.** `get_config()` (`paws.common/R/config.R`) looks at the *calling expression* (`svc$op(...)`) and evaluates `svc` in the caller's frame to read `svc$.internal$config`. A custom function that calls `s3_upload_part(...)` directly gets a default `Config()`, silently losing the user's credentials/region/endpoint. Capture `config <- get_config()` first thing, rebuild a client with `svc <- .s3$operations; svc$.internal <- list(config = config)`, and call operations as `svc$upload_part(...)` from a frame where `svc` is a visible variable (not via `do.call`). See `s3_upload_file`.
- **`Config()` struct defaults of `NULL` arrive as zero-length vectors, not `NULL`.** Once a config has passed through `set_config()`/`populate()`, an unset optional field such as `s3_payload_signing_enabled` is e.g. `logical(0)`. Test for a set value with `is.logical(x) && length(x) == 1 && !is.na(x)`, not `!is.null(x)`. Unit tests that build `Config()` directly won't show this; add a test that goes through a real client config (this bug shipped once and made every S3 request sign `UNSIGNED-PAYLOAD`).
- **`make.paws`'s own test files source a stale installed copy, not your edit.** `make.paws/tests/testthat/test_generate_presigned_url.R` (and similarly-structured test files) do `source(file.path(system.file("src", "custom", package = "make.paws"), "s3.R"))` — that's the *installed* package's copy (synced from `R/custom/` only by the package's `configure` script at install time), not `make.paws/R/custom/s3.R` on disk. Editing the source file alone will not change what these tests see; reinstall `make.paws` first, or verify changes by sourcing `make.paws/R/custom/s3.R` directly in a throwaway script instead of relying on `testthat::test_file()` through the package.
